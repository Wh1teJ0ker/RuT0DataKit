# 代码质量审计报告 — 低耦合高内聚专项

> **审计目标**：对当前完整代码库（Rust core + Tauri 命令层 + React 前端）做软件工程维度的质量检查，重点评估是否符合「低耦合 / 高内聚」原则。
>
> **审计范围**：截至 v0.4.4 的 68 个 Rust 源文件（~50,362 行）+ 18 个前端源文件（~5,508 行），合计约 55,870 LOC。
>
> **审计方法**：静态分析 — 模块依赖图扫描、文件 LOC/函数密度统计、跨模块 `use` 引用计数、重复正则/函数签名 grep、God 文件识别、前端状态管理结构评估。全部基于源码 grep 与 wc 实测，无运行时假设。
>
> **审计日期**：2026-07-23

---

## 1. 总体结论

| 维度 | 评级 | 一句话结论 |
|------|------|------------|
| 模块分层 | ✅ 良好 | 14 个顶层模块按职责清晰切分，依赖图为无环 DAG |
| 模块耦合 | ⚠️ 可改进 | 无循环依赖，但 `error` / `rules` / `readers` 三个 hub 被跨模块引用过度，存在 hub coupling |
| 模块内聚 | ❌ 多处违规 | 11 个 God 文件 >400 LOC，最大 `blind_aggregator.rs` 1790 行 / 58 函数，混职责 |
| 代码重复 | ⚠️ 可改进 | phone 正则 `^1\d{10}$` / `^1[3-9]\d{9}$` 跨 6+ 文件硬编码；`extract_pattern` 与 validators 双正则源 |
| 前端状态 | ⚠️ 可改进 | `state.js` 385 行单 reducer，29 个 action 全平铺，缺乏领域切片 |
| 总体 | ⚠️ 基本合格但有改进空间 | 架构骨架健康，但若干大文件已到「必须拆分」阈值 |

**核心判断**：低耦合方面表现尚可（无环、分层清晰、`pub use` 重导出规范），**高内聚方面是主要短板** —— 多个文件突破 400-1800 LOC，职责混杂，已威胁可维护性。建议优先处理 God 文件拆分与正则集中化。

## 2. 模块耦合分析

### 2.1 模块分层与依赖图

`crates/core/src/lib.rs` 声明 14 个顶层模块：

```
error / extract / log / logsign / maskers / pcap / pipeline /
readers / report / rules / scan / search / tools / validators
```

依赖图（按 `use crate::<mod>` 出现次数计）：

| 被依赖模块 | use 次数 | 依赖文件数 | 角色 |
|-----------|---------|-----------|------|
| error | 26 | 26 | 全局错误类型 hub |
| readers | 15 | 15 | 文件读取抽象 hub |
| rules | 14 | 15 | 规则类型/算子 hub |
| maskers | 13 | — | 脱敏算子 |
| validators | 12 | — | 校验算子 |
| report | 6 | — | 报告结构 |
| scan | 4 | — | 提取扫描 |
| pcap | 4 | — | 流量包 |
| logsign | 4 | — | 日志签名 |
| log | 4 | — | 日志解析 |
| pipeline | 2 | — | 管道 |

### 2.2 优点：无环 DAG

通过跨模块 `use crate::` 引用扫描构造依赖图，**未发现循环依赖**。拓扑顺序清晰：`error → report → readers → rules/validators/maskers → pipeline/scan → logsign/log/pcap → tools`。这是低耦合的正面证据。

### 2.3 问题：三大 hub 耦合

`error`（26 文件）、`rules`（15 文件）、`readers`（15 文件）三个模块被几乎所有业务模块引用，形成 **hub coupling（星型耦合）**：

- **`error` 被引用 26 次**：几乎所有模块都依赖 `crate::error::{DataError, Result}`。这本身是常见模式（全局错误类型），但 `error` 模块若扩张（如加入领域特定错误枚举），改动会波及全局。
- **`rules` 被引用 15 次**：`FieldRule` / `MaskRule` / `RuleSet` 类型被 `pipeline` / `scan` / `validators` / `maskers` / `extract` / `tools` 等多模块直接消费。规则类型既是数据模型又是跨层契约，任一字段变更 ripple 范围大。
- **`readers` 被引用 15 次**：`RecordsReader` trait + 各格式 reader 被 `pipeline` / `extract` / `search` / `pcap` / `log` 等消费。

**风险**：hub 模块变更成本高。`error` 改签名要动 26 个文件；`rules` 加字段要同步 15 处。

### 2.4 改进建议（耦合）

1. **`error` 引入领域子模块**：拆为 `error::io` / `error::rule` / `error::scan` 等子枚举，业务模块只 `use` 自己的子错误，减少全局 hub 牵连。
2. **`rules` 类型下沉为 `rules::types` 子模块**，消费方按需引用，避免整包导入。
3. **`readers` 的 `RecordsReader` trait 保持稳定，但具体 reader 实现分文件**（已部分做到），继续禁止跨 reader 互相 `use`。

## 3. 高内聚评估 — God 文件清单

### 3.1 识别标准

文件 LOC > 400 且函数密度高，即视为 God 文件（职责过载、内聚度低）。共识别 **11 个**：

| # | 文件 | LOC | 函数/命令数 | 主要职责混杂点 |
|---|------|-----|-----------|---------------|
| 1 | `crates/core/src/logsign/blind_aggregator.rs` | 1790 | 58 函数 | 盲注探针解析 + 位置聚类 + true_size 众数算法 + 数据库还原 + 4 类 read_target 解析 + 正则缓存，全堆一文件 |
| 2 | `src-tauri/src/commands.rs` | 1173 | 32 个 `#[tauri::command]` | 全部 32 个 Tauri 命令平铺单文件，跨脱敏/校验/日志/pcap/搜索/提取/工具/设置 8 个领域 |
| 3 | `crates/core/src/rules/operator.rs` | 976 | 41 函数 | 4 种 MaskOp + 3 种 ValidateOp + `from_rule` 构造 + 参数解析 helpers，混在一个 enum/impl 块 |
| 4 | `frontend/src/components/LogView.jsx` | 770 | — | 日志表格 + 攻击分类 Tag + 解析结果列 + decoded 三列 + 盲注聚合卡片 + 还原数据库表，单组件 770 行 |
| 5 | `crates/core/src/tools/regex_explain.rs` | 635 | — | 正则 token 解析 + 说明生成 + 多种 token 类型匹配 |
| 6 | `crates/core/src/pipeline/mask.rs` | 534 | — | 脱敏管道 + 4 种算子执行 + 列选择 + 摘要 |
| 7 | `frontend/src/components/MaskView.jsx` | 500 | — | 表头映射 UI + 算子下拉 + 参数表单 + 试运行 + 结果表 |
| 8 | `frontend/src/components/ValidateView.jsx` | 478 | — | 与 MaskView 结构高度相似（重复模式） |
| 9 | `crates/core/src/pipeline/log_scan.rs` | 460 | — | 日志扫描管道 + SQLi 签名匹配 + 敏感词扫描 + 报告聚合 |
| 10 | `crates/core/src/tools/sql_parse.rs` | 442 | — | SQL 解析 + 盲注特征检测 + payload 提取 |
| 11 | `frontend/src/components/RegexTool.jsx` | 432 | — | 解析/构造双 Tab + 输入输出 + 示例 |

### 3.2 重点 God 文件详解

#### 3.2.1 `blind_aggregator.rs`（1790 LOC / 58 函数）— 最高优先级拆分

该文件混了 **三层职责**：

1. **探针抽取层**：`looks_like_blind_probe` / `extract_blind_probe_with_line` + 三套正则（ascii_binary / equality / length）。
2. **聚合算法层**：`aggregate_position` / `aggregate_ascii_binary_group` / `mode_per_position_true_size` / `build_decoded_string` 等位置聚类与 true_size 众数判定。
3. **数据库还原层**：`reconstruct_database` + `parse_table_name_predicate` / `parse_from_table` / `parse_row_data_columns` / `build_table_columns_and_rows` + 3 个 `ReconstructedDatabase/Table/Row` 结构体。

应拆为：
- `logsign/blind/probe.rs`（探针抽取 + 正则）
- `logsign/blind/aggregate.rs`（位置聚类 + true_size 算法）
- `logsign/blind/reconstruct.rs`（数据库还原 + read_target 解析）

#### 3.2.2 `commands.rs`（1173 LOC / 32 命令）— 按领域拆分

32 个命令覆盖 8 个互不相关领域，单文件无内聚可言。按 `src-tauri/src/commands/` 目录拆为：

| 子文件 | 命令 |
|--------|------|
| `mask.rs` | `apply_rules_cols` / `apply_rules_cols_records` |
| `validate.rs` | `run_validate` / `run_validate_records` |
| `export.rs` | `export_records_csv` / `_xlsx` / `_json` |
| `ruleset.rs` | `save_ruleset` / `read_ruleset` / `list_rule_tags` / `list_builtin_rules` |
| `log.rs` | `scan_log_file` |
| `pcap.rs` | `scan_pcap_file` / `detect_tshark` / `load_tshark_path` / `save_tshark_path` |
| `extract.rs` | `extract_text` / `extract_file` / `export_extract` |
| `search.rs` | 搜索相关命令 |
| `tools.rs` | `parse_sql` / `explain_regex` / `construct_regex` |

#### 3.2.3 `operator.rs`（976 LOC / 41 函数）

`MaskOp`（4 变体）与 `ValidateOp`（3 变体）虽都实现 `from_rule`，但职责正交。应拆为 `rules/mask_op.rs` + `rules/validate_op.rs`，各自承载 `from_rule` 与参数解析 helpers。

### 3.3 改进建议（内聚）

1. **优先拆 `blind_aggregator.rs`**：1790 行是全库最大文件，三层职责清晰可切。
2. **`commands.rs` 按领域分文件**：32 命令平铺是维护负担，每次加命令都在 1173 行里翻找。
3. **`operator.rs` 按算子族拆分**：MaskOp/ValidateOp 正交，无理由同居。
4. **前端 `LogView.jsx` 770 行拆子组件**：聚合卡片、还原数据库表、decoded 列各抽独立组件。
5. **`MaskView.jsx` 与 `ValidateView.jsx` 抽公共 `<ColumnRuleMapper>`**：两者结构高度重复，应抽共享组件降重复。

## 4. 代码重复分析

### 4.1 Phone 正则跨 6+ 文件硬编码

`^1\d{10}$` 与 `^1[3-9]\d{9}$` 两个 phone 正则在以下文件各自硬编码：

| 文件 | 出现 | 用途 |
|------|------|------|
| `crates/core/src/validators/phone.rs` | `^1\d{10}$` | PhoneValidator 校验 |
| `crates/core/src/scan/mod.rs` | `\b\d{11}\b`（extract_pattern） | 提取候选 |
| `crates/core/src/rules/operator.rs` | `^1\d{10}` 注释 + 守卫 | RegexWithGuard |
| `crates/core/src/rules/builtin.rs` | 注释引用 | 内置规则文档 |
| `crates/core/src/tools/regex_template.rs` | `^1[3-9]\d{9}$` | 正则模板示例 |
| `crates/core/src/tools/regex_explain.rs` | `^1[3-9]\d{9}$` | 测试 + 说明 |
| `crates/core/src/tools/regex_construct.rs` | `^1\d{10}$` | 构造测试 |
| `frontend/src/components/SearchView.jsx` | placeholder | UI 提示 |
| `frontend/src/components/RegexTool.jsx` | placeholder | UI 提示 |

**风险**：phone 校验规则若变更（如加号段），需改 6+ 处，易遗漏。且 `^1\d{10}$`（validators）与 `^1[3-9]\d{9}$`（tools）语义不一致，存在潜在 bug。

### 4.2 `extract_pattern` vs validators 双正则源

`scan/mod.rs:52` 的 `extract_pattern(scope)` 返回提取用正则（如 phone → `\b\d{11}\b`），而 `validators/phone.rs` 内部另有校验正则 `^1\d{10}$`。**同一 scope 有两套正则定义在不同模块**，语义割裂：

- 提取正则（宽松，召回候选）在 `scan`
- 校验正则（严格，过滤误报）在 `validators`

这本身是合理的两阶段设计，但两套正则无集中注册表，新增 scope 要同步改两处且无编译期保障。

### 4.3 改进建议（重复）

1. **建立 `rules/patterns.rs` 集中正则常量表**：每种 scope 的 extract + validate 正则集中定义，`scan` 与 `validators` 共享引用，消除硬编码散布。
2. **`scope` 枚举化**：当前 `scope: String` 无编译期约束，拼错不会报错。改为 `#[derive(strum::EnumString)] enum Scope` 可静态防误。

## 5. 前端状态管理评估

### 5.1 `state.js`（385 LOC / 29 action）

单 `useReducer` 持有全部应用状态，`initialState` 含 35+ 字段，`appReducer` switch 覆盖 29 个 action type，全部平铺无分组：

- 文件导入（`SET_FILE` / `SET_RECORDS`）
- 脱敏（`SET_MASKED` / `SET_MASK_OVERRIDE` / `CLEAR_*`）
- 校验（`SET_VALIDATE` / `SET_VALIDATE_OVERRIDE`）
- 日志（`SET_LOG_*`）
- pcap（`SET_PCAP_*`）
- 规则（`SET_RULES` / `SET_RULES_TAG_FILTER`）
- 搜索（`SET_SEARCH_*` × 7）
- 工具（`SET_TOOLS_*` / `SET_SQL_*` / `SET_REGEX_*` × 6）
- 提取（`SET_EXTRACT_*` × 5）
- 设置（`SET_TSHARK_*` × 3）
- 导出（`SET_EXPORT_*` / `SET_COLUMN_*` / `SET_SELECTED_*`）
- 导航/UI（`SET_VIEW` / `SET_HINT` / `SET_LOADING` / `RESET`）

### 5.2 问题

- **单 reducer 35+ 字段无切片**：任意 action 触发 `...state` 浅拷贝整个对象，虽 React 性能尚可，但认知负担高 —— 改一个领域要通读 385 行找相关 case。
- **action 命名前缀不统一**：`SET_LOG_ENTRIES` vs `SET_PCAP_ENTRIES` vs `SET_EXTRACT_RESULT`，无领域分组。
- **`SET_FILE` 副作用混杂**：在 reducer 内清空 `maskedRows` / `validateResult` / `maskOverrides` / `validateOverrides` / 重置列选择，这是业务逻辑混入 reducer。

### 5.3 改进建议

1. **按领域切片**：用 `useReducer` + `combineReducers` 模式（或拆为多个 `useReducer`），每个领域独立 reducer（`fileReducer` / `maskReducer` / `logReducer` / `searchReducer` ...）。
2. **action 常量化**：29 个字符串字面量抽为 `const ACTION = { FILE: { SET: "SET_FILE" }, ... }` 常量对象，防拼写错误。
3. **副作用外移**：`SET_FILE` 内的级联清空改为在调用方显式 dispatch 多个 action，或用 effect 处理，保持 reducer 纯函数。

## 6. 其他观察

### 6.1 正面

- **`pub use` 重导出规范**：各模块 `mod.rs` 用 `pub use` 统一对外暴露路径，消费方无需关心子文件结构。
- **测试覆盖充分**：`crates/core/tests/` 下 e2e.rs 2625 行 + 多个专项测试文件，总测试数 445 全绿。
- **文档注释密度高**：模块级 `//!` 与函数级 `///` 注释覆盖率高，意图清晰。
- **Cargo.toml 依赖精简**：core 仅 7 个直接依赖，无冗余。

### 6.2 待改进

- **`scope: String` 弱类型**：应枚举化（见 4.3）。
- **`tag: String` 同上**：三选一字符串，可枚举。
- **`MaskView.jsx` / `ValidateView.jsx` 结构重复**：表头映射 + 算子下拉 + 参数表单 + 试运行模式高度相似，应抽 `<ColumnRuleMapper>` 公共组件。
- **`commands.rs` 单文件 32 命令无 `mod` 分组**：见 3.2.2。

## 7. 优先级重构路线图

按「影响面 × 实施成本」排序，建议分 5 步推进：

| 优先级 | 重构项 | 影响面 | 成本 | 预期收益 |
|--------|--------|--------|------|---------|
| P0 | 拆 `blind_aggregator.rs` 1790 → 3 子文件 | logsign 模块 | 中 | 消除最大 God 文件，提升可读性 |
| P0 | 拆 `commands.rs` 32 命令 → 8 子文件 | src-tauri | 低 | 每加命令只动一个领域文件 |
| P1 | 建 `rules/patterns.rs` 集中正则表 | core 全局 | 中 | 消除 phone 正则 6+ 处硬编码 |
| P1 | 拆 `operator.rs` MaskOp/ValidateOp | rules 模块 | 低 | 两个正交算子族独立 |
| P2 | 前端 `state.js` 按领域切片 | frontend | 中 | 降认知负担，action 分组 |
| P2 | 抽 `<ColumnRuleMapper>` 公共组件 | frontend | 中 | 消除 MaskView/ValidateView 重复 |
| P3 | `scope`/`tag` 枚举化 | core + frontend | 中 | 编译期防误 |

## 8. 审计结论

**整体评价**：架构骨架健康（无环 DAG、分层清晰、`pub use` 规范、测试覆盖充分），**低耦合方面基本达标**。**高内聚方面存在明确短板** —— 11 个 God 文件、正则散布、前端单 reducer 是主要技术债。其中 `blind_aggregator.rs`（1790 LOC）与 `commands.rs`（1173 LOC / 32 命令）已到「必须拆分」阈值，建议作为 P0 优先处理。

**审计结论**：`qualified_pass` —— 代码可用、架构合理，但存在可量化的内聚度缺陷，建议按 §7 路线图在后续版本迭代中消解技术债。
