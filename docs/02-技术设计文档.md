## 2. 关键模块职责

### 2.1 rules

- `RuleSet { validators: Vec<FieldRule>, maskers: Vec<MaskRule> }`，从 YAML 反序列化。
- `Validator` trait：`fn validate(&self, value: &str) -> ValidationResult`。
- `Masker` trait：`fn mask(&self, value: &str) -> String`。
- 内置校验器注册表（`ValidatorRegistry`）：name → 工厂函数。
- 内置脱敏器注册表（`MaskerRegistry`）：同上。
- 自定义规则：v0.2.x 仅支持引用内置 validator/masker；YAML 中可声明 `regex:` 做正则兜底校验。
- 可扩展算子模型（T0-21 增）：`rules::operator` 模块定义两个通用算子枚举，作为内置 masker/validator 的统一收敛点，对外暴露稳定的可扩展 API：
  - `MaskOp`（4 种）：`Template` / `SplitTemplate` / `RegexReplace` / `ConstReplace`。配套 `MatchMode { All, First }`、`MaskOp::from_rule(name, params)` 构造器、`apply_mask_op(op, value)` 应用函数。11 个旧 masker 名（含 6 预设 `idcard_mask` / `phone_mask` / `bankcard_mask` / `email_mask` / `name_mask` / `customer_id_mask` + 富规则 `custom` / `regex_replace` / `regex_extract` / `delete` / `replace`）均收敛到这 4 种算子。
  - `ValidateOp`（3 种）：`Regex` / `Algorithm` / `RegexWithGuard`。配套 `AlgoKind` / `GuardKind`、`ValidateOp::from_rule(rule)` 构造器、`apply_validate_op(op, value)` 应用函数。8 个旧 validator 名收敛到这 3 种算子（`Algorithm` / `RegexWithGuard` 委托给既有 `IdCardValidator` / `BankCardValidator` / `PhoneValidator` / `MacValidator` 结构体，复用既有算法实现）。
  - `rules::presets` 模块提供 `lookup_mask_preset(name)` / `lookup_validate_preset(name)` 预设查表，以及 `list_mask_op_types()` / `list_validate_op_types()` 列举所有可识别名（含预设别名，保证 YAML 向后兼容）。
  - T5-1 增：`rules::presets` 提供 `list_tagged_presets(tag: &str) -> Vec<PresetEntry>`，按标签（`mask` / `validate` / `sensitive` / `search` / `sql_parse`）返回预置模板元信息。`PresetEntry { name, label, tags, params_template: Option<serde_yml::Mapping> }` **不构造 `MaskOp` / `ValidateOp` 实例**，避免与 `operator.rs` 耦合，仅供 GUI（T5-4）预填参数 / 生成规则草稿。
  - `build_masker` / `build_validator` 签名与行为不变，内部改走 `Op::from_rule → apply_*_op` 路径；旧 `Masker` / `Validator` trait、`MaskRule` / `FieldRule` / `RuleSet` 结构、`mask_pipeline*` / `validate_pipeline` 全部保持原样。

### 2.2 readers

```rust
pub trait SourceReader {
    fn detect(path: &Path) -> bool;        // 后缀 / magic
    fn read(&self, path: &Path) -> Result<Records>;
}
```

`Records` = 行流（每行 `Vec<(String, String)>` 字段名→值），csv/xlsx 都映射到它。v0.2.0/v0.3.0 的 log/pcap 不强制走该 trait（它们没有"字段名→值"结构），但复用其读取抽象思路，各自定义独立 output。

**v0.4.0 预处理归一化（T5-2）**：新增 `SqlReader` / `JsonReader`，以及把 pcap / log 模块原 output 包成 `Records` 的适配器 `PcapRecordsReader` / `LogRecordsReader`，不动 pcap / log 模块内部实现。统一入口 `read_records(path: &Path) -> Result<Records, CoreError>` 按 `detect_type` 后缀 dispatch 到对应 reader；`SourceType` 扩 `Sql` / `Json` 变体；Tauri 新增 `preprocess_file(path: String) -> Result<Value, String>` 命令，把任意支持格式统一读成 `{ headers, rows, source_type, row_count }` JSON，供 PreviewView / mask / validate / export 复用。

- `SqlReader`：`.sql` 按 `;` 拆语句（处理单/双引号字符串内分号、跳过 `--` 行注释），每条非空语句一行；headers = `["sql_text", "statement_type"]`，`statement_type` 按首关键字小写判定（select/insert/update/delete/create/alter/drop/other）。块注释、SQL `''` 转义留 v0.4.1+。
- `JsonReader`：JSON 数组对象 → headers=对象 keys 并集（按首次出现序）+ rows，缺失 cell 补 `""`；JSON 单对象 → 1 行；JSON Lines（每行一对象）→ 同数组；纯标量数组 / 字符串 → 单列 `value`。嵌套对象 / 数组最小实现 `to_string()` 成 JSON 串放入单 cell，留 v0.4.1+。
- `PcapRecordsReader`：调 `pcap::PcapReader::read` 拿 `Vec<HttpRequest>` → 8 列 Records（frame_no/src_ip/dst_ip/method/host/uri/body/user_agent），`body=None` → `""`。tshark 缺失时透传 `CoreError::DependencyMissing("tshark")`，不 panic。
- `LogRecordsReader`：调 `log::LogReader::read` 拿 `Vec<LogEntry>` → 12 列 Records（line_no/ip/timestamp/method/path/query/status/size/user_agent/decoded_path/decoded_query/decoded_ua，不含 raw），`query/size/decoded_query` 为 `None` 时 cell 为 `""`。

### 2.3 maskers（内置，v0.1.0 必交付）

| name | 规则 |
|------|------|
| idcard_mask | 前6+后4，中间8位 `*` |
| phone_mask | 前3+后4，中间4位 `*` |
| bankcard_mask | 前6+后4，中间 `*` |
| email_mask | 本地部分首末字符保留，中间 `*`；域名完整 |
| name_mask | 2字→`X*`；≥3字→`X*…*Y` |
| customer_id_mask | 首字符保留，其余 `*` |
| custom | YAML 提供 `keep_prefix / keep_suffix / mask_char / mask_min_len` 通用参数 |
| regex_replace | 富规则：`pattern` 正则 + `replacement`（支持 `$1`/`$2` 捕获组）；非法/缺失 pattern 时原值返回 |
| regex_extract | 富规则：`pattern` 正则提取首个匹配子串；无匹配返回原值 |
| delete | 富规则：对任意输入返回空串 `""`，无参数 |
| replace | 富规则：对任意输入返回 `with` 字符串；缺失 `with` 时退化为空串 |

> 富规则（`regex_replace` / `regex_extract` / `delete` / `replace`）由 v0.1.0 重构（T0-10）落地，经 `build_masker` 统一 dispatch，可与 7 个内置 masker 混挂在同一 `RuleSet.maskers` 中。

**抽象算子模型（T0-21 增）**：

- `MaskOp` 枚举 4 variant：`Template(TemplateOp)` / `SplitTemplate(SplitTemplateOp)` / `RegexReplace(RegexReplaceOp)` / `ConstReplace(ConstReplaceOp)`；配套 `MatchMode { All, First }`。
- 公共 API：`apply_mask_op(op: &MaskOp, value: &str) -> String`；`MaskOp::from_rule(name, params) -> Option<MaskOp>` 构造器；`MaskOp` impl `Masker` trait，可直接作为 `Box<dyn Masker>` 注入 pipeline。
- 预置库（`rules::presets`）：`lookup_mask_preset(name) -> Option<MaskOp>` + `list_mask_op_types() -> Vec<(op_name, label)>`（10 项 = 4 通用算子 + 6 预置别名 `idcard_mask` / `phone_mask` / `bankcard_mask` / `customer_id_mask` / `name_mask` / `email_mask`）。
- `build_masker` 内部走 `MaskOp::from_rule` 路径，签名与行为不变；旧 `MaskRule` / `RuleSet` / `mask_pipeline*` 全部保留向后兼容。
- 新增脱敏类型 = 加一个 `MaskOp` variant + 在 `rules::presets` 加一行映射，`build_masker` 自动 dispatch，无需改 pipeline 或前端调用约定。

**按列勾选脱敏 pipeline（T0-15 增）**：

```rust
pub fn mask_pipeline_columns(
    records: &Records,
    rules: &RuleSet,
    selected_columns: &HashSet<String>,
) -> Result<MaskResult, CoreError>;
```

只对同时满足「在 `selected_columns` 中」且「在 `rules.maskers[].field` 中」的字段应用 masker；未勾选的规则列原样；`selected_columns` 中未声明规则的列原样；未知名 masker 静默跳过。返回与 `mask_pipeline` 同形 `MaskResult`，`summary.by_field` 只统计实际被 masker 调用的字段。

向后兼容：旧 `mask_pipeline` / `mask_pipeline_selected`（行选择）保留不动，三者共用 `build_masker` dispatch 与 `MaskResult` 产出结构。

### 2.4 validators（内置，v0.1.0 留接口+注册表，具体实现可按需提前到 v0.1.0 或后置）

| name | 规则 |
|------|------|
| idcard | 18位，地址码+出生日期码(YYYYMMDD 有效)+顺序码+校验码(weights `[7,9,10,5,8,4,2,1,6,3,7,9,10,5,8,4,2]`, mod 11 查表 `10X98765432`) |
| phone | 11 位数字，首位 1（v0.4.3 去绝对化后仅按 PDF spec `^1\d{10}$` 校验；旧 `prefix_set: ctf\|real` 白名单已删除，见 §2.15） |
| bankcard | 13..19 位数字 + Luhn 校验 |
| email | 标准邮箱正则 |
| mac | 通用 `([0-9A-Fa-f]{2}[:-]){5}[0-9A-Fa-f]{2}`；可加 `prefix` 约束 |
| ip | IPv4，禁前导零，0..255（v0.4.3 起注册为内置校验器，见 §2.15） |
| username | `^[A-Za-z0-9]+$` |
| name | 全中文 `^[\u4e00-\u9fa5]+$` |
| birth | 8位 YYYYMMDD |
| address | 全中文 + 号(1-1500) + 室(101-999) |
| password | 长度≥8 + 大写/小写/数字/符号各一 |

> 说明：v0.1.0 的脱敏 pipeline 不强依赖 validators，但 SensitiveScan 与 v0.2.0 日志扫描会用到。v0.1.0 内至少落地 idcard/phone/bankcard/email/mac/username/name 这几个被脱敏/扫描共用的校验器，其余（birth/address/password）可在 v0.2.0 随日志模块一起补齐；`ip` 在 v0.4.3 起注册为第 8 个内置校验器（见 §2.15.2）。具体由任务 T3-v0.1.0 圈定。

**数据校验 pipeline（T0-15 增，v0.1.0 起 GUI 交付）**：

```rust
pub struct ValidateResult {
    pub headers: Vec<String>,
    pub rows: Vec<Vec<String>>,
    pub valid_matrix: Vec<Vec<bool>>,
    pub summary: ValidateSummary,
}
pub struct ValidateSummary {
    pub total_rows: usize,
    pub invalid_rows: usize,
    pub by_field: HashMap<String, usize>,
}
pub fn validate_pipeline(records: &Records, rules: &RuleSet) -> Result<ValidateResult, CoreError>;
```

逐 cell 填合法矩阵：对 `rules.validators` 中每个 `FieldRule`，`build_validator` 构造校验器并对该列所有 cell 跑 `validate`，非法 cell 置 `false`。未声明 validator 的列 `valid_matrix[*][col]` 全 true；字段不在 `headers` 中或 validator 未知名且无 regex 时该规则静默跳过（不报错）。`summary.invalid_rows` = 至少有一个非法 cell 的行数；`summary.by_field` = 每个声明了 validator 的字段的非法 cell 数。

**抽象算子模型（T0-21 增）**：

- `ValidateOp` 枚举 3 variant：`Regex(RegexOp)` / `Algorithm(AlgorithmOp)` / `RegexWithGuard(RegexWithGuardOp)`；配套 `AlgoKind { IdCard, BankCard }` + `GuardKind { PhonePrefix { prefix_set }, MacPrefix { prefix } }`。
  - **v0.4.3 起向后兼容说明**：`GuardKind::PhonePrefix { prefix_set }` 字段仅作向后兼容保留；`PhoneValidator` 已删除 CTF/real 白名单逻辑（见 §2.15.1），`prefix_set` 取值不再影响校验结果，校验仅按 PDF spec `^1\d{10}$` 进行。旧 YAML 含 `prefix_set` 字段仍可加载不报错。
- 公共 API：`apply_validate_op(op: &ValidateOp, value: &str) -> ValidationResult`；`ValidateOp::from_rule(rule) -> Option<ValidateOp>` 构造器；`ValidateOp` impl `Validator` trait，可直接作为 `Box<dyn Validator>` 注入 pipeline。
- 预置库（`rules::presets`）：`lookup_validate_preset(name, params, message) -> Option<ValidateOp>` + `list_validate_op_types() -> Vec<(op_name, label)>`（10 项 = 3 通用算子 + 7 预置别名 `email` / `username` / `name` / `idcard` / `bankcard` / `phone` / `mac`）。`Algorithm` / `RegexWithGuard` 委托既有 `IdCardValidator` / `BankCardValidator` / `PhoneValidator` / `MacValidator` 复用算法实现。v0.4.3 起 `IpValidator` 注册为第 8 个内置校验器（见 §2.15.2）。
- `build_validator` 内部优先走 `ValidateOp::from_rule`（覆盖 regex 兜底 + 7 个预置别名），未命中时回退 `ValidatorRegistry`；签名与行为不变。

### 2.6 report（统一 schema，v0.1.0 落地）

```rust
pub struct Report {
    pub source: String,
    pub kind: String,             // "csv_mask" | "csv_validate" | "log" | "pcap"
    pub summary: serde_json::Value,
    pub findings: Vec<Finding>,
    pub extra: serde_json::Map<String, serde_json::Value>,
}
pub struct Finding {
    pub r#type: String,           // idcard/phone/...
    pub value: String,
    pub location: Option<String>,
    pub valid: Option<bool>,
    pub context: Option<String>,
    #[serde(skip_serializing_if = "Option::is_none")]
    pub extra: Option<serde_yml::Value>,
}
```

v0.1.0 脱敏报告 `kind="csv_mask"`，summary 含 `{ total_rows, masked_rows, by_field: {field: count} }`，findings 可为空（脱敏不产出 finding，但结构统一）。

T2-9（v0.2.0）为 `Finding` 增 `extra: Option<serde_yml::Value>`（`skip_serializing_if = "Option::is_none"`，
向后兼容：无 extra 时序列化形态不变）。log_scan pipeline 的 sqli finding 把 `SignatureHit.parsed_payload`
序列化为 `serde_yml::Value` 透传进 `extra`，供前端展示「解析结果」「读取目标」等列；weak_password /
sensitive / csv_mask 场景 extra 为 `None`（序列化时不出现 `extra` key）。

### 2.7 pcap（v0.3.0）

- `PcapScanner::scan(path, rules) -> Report`
- 内部：tshark 子进程 → TSV → HttpRequest → 双重 URL 解码 → base64 重组 → 敏感扫描。
- tshark 不存在时返回 `CoreError::DependencyMissing("tshark")`，不 panic。

### 2.8 log（v0.2.0）

- 入口：自由函数 `scan_log(entries, sig_engine, scan, rules) -> Report`（`crates/core/src/pipeline/log_scan.rs`），`src-tauri/src/commands.rs::scan_log_file(path) -> {entries, report}` 为 IPC 包装。
- CLF 解析 → `LogEntry { ip, ts, method, path, query, status, ua }`。
- 攻击特征（内置签名，v0.2.0 范围）：SQLi 6 类（盲注二分 / UNION / 报错 / 时间盲注 / 恒真 / 注释符）+ 弱口令关键字 grep（16 项等值匹配）。**路径穿越 / 命令注入 / 越权**未实现，留待 v0.3.0+ 评估。
- 对 query / ua 跑敏感扫描（复用 v0.1.0 `DefaultSensitiveScan`；默认 RuleSet validators 为空时 sensitive_hits=0，字段存在兜底为 0）。

### 2.8.1 logsign（v0.2.0，SQLi 签名引擎）

- 独立模块 `crates/core/src/logsign/`，与 `rules` 解耦，不引用 `MaskOp` / `ValidateOp` / pipeline。
- `SignatureRule`（YAML 反序列化形态）：`rule_id / category / pattern / enabled / context_anchor: Vec<String> / description`。
- `SignatureHit { rule_id, category, line_no, matched_value, context, parsed_payload }`。
  `parsed_payload: Option<ParsedPayload>` 在 `scan_log_entry` 产 hit 时对命中文本段
  调 `payload_parser::parse_payload(text)` 填充，未解析到为 `None`。
- `SignatureEngine::new()` 用 `include_str!` 编译期嵌入的内置 YAML 加载 6 条 SQLi 签名：
  `sqli_blind_binary / sqli_union / sqli_error_based / sqli_time_based / sqli_tautology / sqli_comment`。
- `scan_log_entry(&LogEntry) -> Vec<SignatureHit>`：
  - 跳过 `method.is_empty() || path.is_empty()` 的行（408 超时行），不产 finding；
  - 匹配目标 = `path` + `parse_query(query)` 的所有 value（已双重 URL 解码），故 pattern 一律按 decoded 形态编写；
  - `context_anchor` 非空时要求所有锚点也在该段文本中命中才算命中（抑制 `or` / `--` 弱信号误报）；
  - 同一规则在同一文本段命中只产 1 个 `SignatureHit`。
- `loader::load_signatures_from_str(&str)` 提供运行时反序列化入口，供 T2-5 GUI 在线编辑后重新装载。
- 零新依赖：复用 core 已依赖的 `serde_yml`。

### 2.8.2 payload_parser（v0.2.0，SQLi payload 语义解析）

- 独立模块 `crates/core/src/logsign/payload_parser.rs`，对命中后的 decoded 文本做
  结构化语义解析，与签名匹配（判类别）互补。
- `ParsedPayload { attack_type, technique, read_target, char_position, compared_ascii,
  comparator, union_columns, sleep_seconds, summary }`，derive `Debug/Clone/PartialEq/Eq/Serialize`。
- `parse_payload(decoded_text: &str) -> Option<ParsedPayload>`：
  - 输入应为已解码文本（`+` 已空格、`%XX` 已解）；内部先 `to_lowercase()` 再匹配，兼容大写 SQL。
  - 6 类正则（regex crate 无 look-around，吃前缀 + 捕获组）按 blind → union → error →
    time → tautology → comment 顺序首命中返回，一条 payload 只归一类。
  - blind_boolean：`ascii(substr((<func>),N,1)) <cmp> <ascii>` → read_target/char_position/
    comparator/compared_ascii；summary「盲注二分：…」。
  - union：`union [all ]select N,N,…` → union_columns（数逗号+1）；summary「UNION 注入：取 N 列」。
  - error：`(extractvalue|updatexml)(N,concat(…, <func>))` → read_target；summary「报错注入：…」。
  - time：`(sleep|benchmark|pg_sleep)(N)` → sleep_seconds；summary「时间盲注：延时 N 秒」。
  - tautology：`<or|and> N=M` → summary「恒真绕过：N=M」。
  - comment：`(--|#|/\*)` → summary「注释符截断查询：…」。
- 与 `SignatureHit` 集成方式：`scan_log_entry` 产 hit 处直接调 `parse_payload(text)`，
  结果写入 `parsed_payload` 字段，供 T2-9 pipeline 转入 `Finding` 时复用。

### 2.8.3 v0.2.1 语义增强（T2-7 ~ T2-10）

- **`parse_query` `+` 解码语义（T2-7）**：`crates/core/src/log/mod.rs::parse_query` 按
  form-urlencoded 标准 `+`→space 再双重 `%XX` 解码（`url_decode_twice`）。
  - 历史口径（v0.2.0）：`parse_query` 不解 `+`，pattern 一律按含 `+` 形态编写；

### 2.8.4 blind_aggregator（v0.2.2，盲注二分序列聚合还原）

- 独立模块 `crates/core/src/logsign/blind_aggregator.rs`，与 `payload_parser` 互补：
  payload_parser 只解析单条 payload 的语义类别（盲注/UNION/报错…），本模块在签名
  命中之后对一批同源（同 `read_target` + 同 `source_ip`）的二分探针按 `char_position`
  聚类，还原出被盲注读取的完整字符串（flag）。
- 输入：`BlindAggregator::collect_from_entries(&[LogEntry])` 对每条 entry 的
  `decoded_query`（None 则 `decoded_path`）整串跑自带正则，抽出
  `ascii(substr((<read_target>),<pos>,1))<cmp><thr>` 形态的探针；`body_size` 取
  `LogEntry.size`（`Option<u64>`，`None` 跳过该 entry）；`source_ip` = `LogEntry.ip`。
- 结构（derive `Serialize`，承载 `Report.extra.blind_aggregation`）：
  - `BlindProbe { read_target, char_position, threshold, body_size, source_ip, line_no }`。
  - `PositionDetail { position, decoded_char, ascii_val, true_size, probe_count, status }`
    （status ∈ `resolved` / `unresolved_all_true` / `beyond_end` / `insufficient_probes`）。
  - `AggregatedResult { read_target, decoded_string, resolved_chars, unresolved_chars,
    beyond_end_positions, probe_count, source_ips, position_details }`。
- bytes 自动聚类算法（fixture-specific 假设）：
  - 对每个 `(read_target, source_ip)` 分组：`group_true_size = min(所有探针 body_size)`
    （条件成立响应 body 更小，实测 fixture line 19-65：thr=79/103/109/111 → body=862 true，
    thr=112/115 → body=875 false）。
  - 按 `char_position` 子分组；全同 body 且 == group_true_size → `unresolved_all_true`；
    全同 body 且 != group_true_size → `beyond_end`；混合则 true 探针 = `body == true_size`
    （ascii > thr），false 探针 = `body != true_size`（ascii <= thr），
    `ascii_val = min(false_thresholds)`，自洽性校验 `max(true_thresholds) + 1 == ascii_val`，
    不符标 `insufficient_probes`。
  - 按 position 升序拼接：resolved 追加字符；unresolved/insufficient 追加 `'?'`；
    **首个 `beyond_end` 即停止拼接**（字符串末尾）。
  - 该方向是 fixture-specific 假设；若未来接入「条件成立 → body 更大」的靶机，
    需把取法从 `min` 改为 `max`（见模块注释）。
- 自带嵌套正则：regex crate 无 look-around，`read_target` 内层嵌套括号用
  `(?:[^()]|\([^()]*\))*` 吃掉单层 `(...)`（如 `database()` / `group_concat(table_name)`）；
  多层嵌套不支持，是已知简化。
- 与 `Report.extra` 集成（T2-13）：`scan_log` 末尾把 `Vec<AggregatedResult>` 序列化进
  `Report.extra` 的 `Value::Mapping({blind_aggregation: [...]})`；无盲注探针时 extra 仍为
  含空数组的 Mapping（前端统一按 sequence 读）。向后兼容：v0.2.1 `Finding.extra` 为
  `Value::Null` / `Option<serde_yml::Value>` 既有行为不破，weak_password / sensitive
  finding `extra=None`（skip_serializing_if 不出现 `extra` key）。
- GUI 集成（T2-14）：`frontend/src/components/LogView.jsx` 新增「盲注聚合结果」段 ③.5，
  读 `Report.extra.blind_aggregation` 渲染 inner Card + Text copyable 还原串 + 探针数 +
  来源 IP + 位置明细 Tooltip + 空态 Empty。

### 2.8.5 blind_aggregator 三轴优化（v0.2.3，T3-1 ~ T3-3）

- **算法优化（T3-1）**：
  - `true_size` 判定由 v0.2.2 的 `min(body_size)`（fixture-specific 假设，反向场景误判）改为
    `mode_per_position_true_size`：按 `char_position` 分组 → 每个「混合位置」取真假两簇 `body_size`

  - `AggregatedResult` 新增 `separator_char: Option<char>`（`#[serde(skip_serializing_if)]`）：

### 2.8.6 blind_aggregator 数据库格式还原（v0.2.4，T4-1 ~ T4-3）

- **新增 3 结构（T4-1）**：
  - `ReconstructedDatabase { schema: Option<String>, tables: Vec<ReconstructedTable>, unmatched_results: Vec<AggregatedResult> }`（`serde::Serialize`，`schema` 用 `skip_serializing_if = "Option::is_none"`）。
  - `ReconstructedTable { name: String, columns: Vec<String>, rows: Vec<ReconstructedRow>, row_data_columns: Vec<String>, column_separator: Option<char>, source_probe_count: u32 }`（`column_separator` skip_serializing_if）。
  - `ReconstructedRow { cells: Vec<Option<String>> }`（与 `columns` 等长，未 fetch 列 `None`）。
- **`reconstruct_database` 算法（T4-1）**：新增 `BlindAggregator::reconstruct_database(&[AggregatedResult]) -> ReconstructedDatabase` 关联函数，三步：
  - **Step1 分类**：对每个 `AggregatedResult` 按 `read_target` 模式分 4 类（regex crate 无 look-around，用 contains + 简单正则）：
    - `schema`：`read_target.trim() == "database()"` → `schema = Some(decoded_string)`。
    - `table_list`：`read_target.contains("group_concat(table_name)") && read_target.contains("information_schema.tables")` → 表名清单，`decoded_string` 按 `,` split。
    - `column_list`：`read_target.contains("group_concat(column_name)") && read_target.contains("information_schema.columns")` → 列名清单，`decoded_string` 按 `,` split；同时正则 `table_name\s*=\s*'([^']+)'` 抽出归属表名（无谓词按表名顺序索引对齐）。
    - `row_data`：`read_target.contains("group_concat(") && !上述两类` → 行数据；用正则 `from\s+(\w+)` 抽表名、`group_concat\s*\(([^)]*)\)` 抽列清单字符串（按 `,` split → tokens，过滤 `0xNN` hex token，剩余为 `row_data_columns`；首个 `0xNN` token 复用 `parse_separator_char` 解码为 `column_separator`）。
    - 未匹配 → 推入 `unmatched_results`。
  - **Step2 拼装**：schema 直填；对 `table_list` 解码出的每个表名 `T`：按 `table_name='T'` 谓词匹配 `column_list`（无谓词按索引对齐）→ `columns` 全量列（无列清单 → `columns = row_data_columns` 兜底）；按 `from T` 匹配 `row_data` → 解析 rows。row 解析：`decoded_string` 按 `,` split → 行字符串数组（group_concat 默认行分隔符）→ 每行按 `column_separator` split → 值数组 → 映射到 `row_data_columns → value` → 投影到 `columns` 全量列，未 fetch 列 `None`。
  - **Step3 unmatched**：未匹配的 `AggregatedResult` 原样塞 `unmatched_results`，前端兜底渲染。
  - 分类正则均 `OnceLock<Regex>` 缓存；辅助函数 `parse_table_name_predicate` / `parse_from_table` / `parse_row_data_columns` / `build_table_columns_and_rows`。8 条单测覆盖全还原 / unmatched / 缺 column_list 兜底 / 空 results / 无分隔符单列 / 3 正则单元测试。
- **pipeline 透传（T4-2）**：`scan_log` 末尾在 `BlindAggregator::collect_from_entries` + `aggregate` 之后调 `BlindAggregator::reconstruct_database(&blind_results)`，结果塞 `Report.extra.reconstructed_database` 键（与 `blind_aggregation` 并列）；`serde_yml::to_value(&reconstructed).unwrap_or(Value::Null)` 透传到前端 JSON。向后兼容 v0.2.3：`blind_aggregation` 数组契约不破，新增 `reconstructed_database` 键。e2e `log_scan_full` 新增五段断言（schema=="person" / 1 表 person_data / 7 列 / ≥2 行 / row[0].id=Some("1") / row[0].username=contains zhangsan/lisi / row_data_columns 含 id/username/idcard / column_separator=="~"）。
- **GUI 显示（T4-3）**：`LogView.jsx` 段 ③.5 之前新增段 ③.5a「还原数据库视图」Card：
  - 顶部 `Descriptions`：数据库名（`schema` `<Text code>`）+ 表数 + unmatched 数。
  - 每张 `ReconstructedTable` 一个 inner Card：title=`<Text code strong>{table.name}</Text>` + 列/行数 Tag；body=antd `Table`（`buildTableColumns` 把 `table.columns` 映射成 antd columns，title=列名，dataIndex=列名，未 fetch 单元格 `render: v => v ?? <Text type="secondary">-</Text>` 显示 `-`；`buildTableDataSource` 把 `table.rows` 映射成 dataSource，每行 object 键=列名，未 fetch 列 undefined）；extra=`column_separator` volcano Tag + `row_data_columns` Tooltip「已 fetch N/M 列」+ 探针 Tag。
  - unmatched_results 非空：`Divider` + 简版列表（read_target + decoded_string copyable）。
  - 空态：`reconstructedDb == null || tables.length === 0` → `<Empty description="无法还原为数据库结构（缺少 database()/table_name/column_name/row data 四类探针）" />`。
  - 段 ③.5 既有逐 RT inner Card（kind Tag / separator 高亮 / Collapse+Table 位置明细）全部保留，Card title 改为「原始聚合明细」作兜底，数据源 `blindAggregation` 不动。
- 向后兼容：`blind_aggregation` 数组契约保留不动；新增 `reconstructed_database` 键 + 新结构字段 `schema`（Option）/ `column_separator`（Option）均 `skip_serializing_if`，旧消费者读不到不影响。

- 改动文件：`frontend/src/components/MaskView.jsx` + `frontend/src/components/ValidateView.jsx`。
- 改动点（两 view 同构）：
  - 删除 `listMaskOpTypes` / `listValidateOpTypes` 调用与 `MASKER_DEFS` / `VALIDATOR_DEFS` / `ParamField` import（这些是算子**模板**元信息来源，与用户规则无关）。
  - 段②「表头-规则映射」下拉源改为 `state.rules.maskers` / `state.rules.validators` 按 tag 筛选后的用户规则子集（MaskView 取 `by_tag_mask("mask")` + 无标签兼容；ValidateView 取 `by_tag("validate")`）。
  - 下拉项 value 用规则在 ruleset 的下标（保证多条同 field 规则可区分），label 摘要为 `field → masker(params=...)` / `field → validator(params=...)`。
  - 选中规则即整条（含 params）作为 override 写入会话级 `maskOverrides` / `validateOverrides`，不再要求用户在视图内重新填参数。
  - 删除原「参数」列，新增「规则摘要」列展示选中规则的 `field → masker(params=...)`。
  - 无规则时显示 `Alert` 引导用户去「规则管理」创建规则，并附「去创建」按钮跳转 RulesView。
  - 顶部文案改为「要改参数请去『规则管理』编辑规则」。
- 根因：原下拉是 `listMaskOpTypes` / `listValidateOpTypes` 返回的算子**模板**清单（template / split_template / regex_replace / const_replace / ...），用户在 RulesView 创建的真实规则根本进不了脱敏/校验视图的下拉，与 v0.4.0 设计「规则管理是单一规则源、脱敏/校验只做映射」的意图不符；用户被迫在 MaskView/ValidateView 内重新选算子 + 填参数，造成规则双源、参数漂移。
- 影响：修复后 MaskView/ValidateView 仅作为「字段→规则」映射面板，参数编辑统一收敛到 RulesView；用户在 RulesView 改了规则参数后，MaskView/ValidateView 下拉摘要自动反映新参数。
- 向后兼容：`listMaskOpTypes` / `listValidateOpTypes` Tauri 命令与 `MASKER_DEFS` / `VALIDATOR_DEFS` 模块保留（RulesView 试运行仍在用），仅从 MaskView/ValidateView 移除调用；`state.maskOverrides` / `state.validateOverrides` 结构与「应用」时合并 override + 全局规则的逻辑不变。

用户诉求（verbatim）：「数据预处理需要可以调用对某一列直接调用如sql解析的功能燃后跳转」。

- 列值输入方式 = 该列全部行（取该列所有非空单元格值作为 `SqlParseInput[]`，跳过空值）。

`frontend/src/components/PreprocessView.jsx` 新增 `handleColumnSqlParse(columnName)` handler：

```js
const handleColumnSqlParse = async (columnName) => {
  if (!records) return;
  const sqls = [];
  for (const row of records.rows || []) {
    const c = records.headers.indexOf(columnName);
    if (c < 0) break;
    const v = row[c];
    if (v == null) continue;
    const s = String(v).trim();
    if (s !== "") sqls.push(s);
  }
  if (sqls.length === 0) {
    message.warning(`列「${columnName}」没有非空值可解析`);
    return;
  }
  const inputs = sqls.map((sql) => ({ sql, responseBodySize: null, sourceIp: null }));
  try {
    const result = await parseSqlTool(inputs);
    const text = sqls.join("\n");
    dispatch({ type: "SET_SQL_PARSE_INPUT", sqlParseInput: text });
    dispatch({ type: "SET_SQL_PARSE_RESULT", sqlParseResult: result });
    dispatch({ type: "SET_VIEW", activeView: "tools" });
    dispatch({ type: "SET_TOOLS_ACTIVE_TAB", toolsActiveTab: "sql" });
  } catch (e) {
    showError(`SQL 解析失败: ${e}`);
  }
};
```

边界：
- 空列：`message.warning`，不跳转。
- 解析失败：`message.error`（实际用 `showError`），不清空已有 `sqlParseInput` / `sqlParseResult`。
- 跳转后不清除原 records（与 Pattern B「RulesView apply-and-jump」一致：`SET_VIEW` 仅切换视图）。
- `SqlParseTool.jsx` 不修改：已读取 `state.sqlParseInput` + `state.sqlParseResult`，预填后用户落地即在 Tools/Sql 看到解析结果，可继续编辑 textarea 重跑。

跳转模式镜像 `Sidebar.jsx:60-62`（`SET_VIEW activeView:"tools"` + `SET_TOOLS_ACTIVE_TAB toolsActiveTab:"sql"`），与 v0.4.1 T6-4「盲注自动跳转」互补——前者是用户针对单列主动触发，后者是导入时按全部 cell 探测后自动跳转。
