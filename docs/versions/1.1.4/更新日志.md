## 本版概要

v1.1.3 把行级多字段校验（T57）做成了独立能力（TopToolbar 单独按钮「行级校验」+ SidePanel 单独面板入口），与单列校验割裂。v1.1.4 初稿曾以 antd `Tabs` 把「单列校验」与「行级校验」并列入 `ValidatePanel`，但仍需用户在两个 Tab 间手动切换、且行级校验固定 7 字段、无法自由组合规则。

本版（T67 + T68 + T69）重做校验模块为**统一校验页面**：用户可动态添加任意多条「目标列 + 校验规则」组合，一个「校验」按钮即把通过 / 失败的行分流到两个新 Tab。身份证规则可勾选跨字段比对性别 / 出生日期。后端新增 `validate_multi_rules_to_two_sheets` 命令承接多规则列式校验。

## 续轮：通用校验 + 地址放宽 + 生日清理 + 前端统一化

### 背景

v1.1.4 首轮（T67/T68/T69）qa_passed 后，用户追加 4 项需求（仍属 v1.1.4）：

1. **通用校验**：新增一种自由组合字符类（纯数字/纯字母/特殊符号）+ 长度限制的通用校验规则。
2. **地址校验放宽**：原 `is_valid_address` 严格正则（号1-1500+室101-999）→ 结构化校验（中文≥2 + 地址关键词，数字不限定范围）。用户经 AskUserQuestion 确认「结构化校验」。
3. **出生日期清理**：原 `is_valid_birth` 只接受 `^\d{8}$` → 先 `clean_birth` 过滤非数字再校验（支持 `20031223` / `2003-12-23` / `2003/12/23` 等）。
4. **前端统一化**：RulesPanel 按规则类型渲染参数 UI（原 validate 规则只显示空正则输入框）；ValidatePanel 按规则行渲染参数配置 + paramsOverride 组装。

### 设计决策

#### 通用校验：ExtractParams::Generic 变体

`ExtractParams` 新增 `Generic` 变体，字段（`#[serde(rename_all = "camelCase")]`）：`allow_digits` / `allow_letters` / `allow_special_chars: String`（`#[serde(default)]`，T77 改为自定义特殊字符白名单）+ `min_len: Option<usize>` / `max_len: Option<usize>`。`allow_special_chars` 空串 = 不允许任何特殊字符；非空如 `"_-.@"` = 仅允许这些字符（白名单语义）。字符类至少有一个非空/为 true（全 false/全空直接判否）；`min_len` / `max_len` 为 `None` 时不限。新增 `generic-validate` 内置规则（`with_defaults()` 16 → 17 条），DB 默认参数 = digits+letters + 特殊符号空 + 长度不限。新增 `is_valid_generic` 函数式校验器：先按字符类白名单逐字符判定（digit/letter + `allow_special_chars.contains(c)`），再校验长度范围。

#### 地址校验放宽：结构化校验

`is_valid_address` 改为：trim 后总长度 4-200；中文字符数（U+4E00..U+9FA5）≥ 2；包含至少一个地址关键词（省/市/区/县/镇/乡/村/路/街/道/号/室/楼/单元/栋/幢/弄/巷/里/组/旗/盟/社区/大厦/小区/花园）；数字不做范围限制。原严格正则（号1-1500+室101-999）废弃。

#### 出生日期清理：clean_birth + 日期有效性

新增 `clean_birth(s: &str) -> String`：按字节过滤保留 ASCII 数字。`is_valid_birth` 改为先 `clean_birth` 再校验 8 位 + 日期范围（年 1900-2100 / 月 1-12 / 日 1-31）。跨字段 birth 比对（`validate_rows_to_two_sheets_inner` + `validate_multi_rules_to_two_sheets_inner`）同步改用 `clean_birth` 归一化，支持 `1949-12-31` 等分隔符格式与 idcard[6..14] 比对。

#### params_override 契约

`validate_extracted` 抽取为 `validate_extracted_with_params(params: &ExtractParams, value: &str) -> (bool, String)`（不依赖 `Rule`，便于覆盖参数）；`validate_extracted(rule, value)` 保留为 wrapper（委托 `validate_extracted_with_params`，向后兼容）。`MultiRuleValidation` 新增 `params_override: Option<ExtractParams>` 字段（`#[serde(default)]` 向后兼容），前端 `ValidatePanel` 每行可下发参数覆盖 DB 默认 params（`validate_multi_rules_to_two_sheets_inner` 优先取 `params_override`，回落 `rule.params`）。

## T67：后端规则系统扩展

### 背景

v1.1.3 的校验能力受限于固定字段映射：行级校验只能对 username/name/sex/birth/idcard/phone/address 7 个固定字段做内置校验，单列校验只能针对一列跑一条规则。用户真正想要的是「自由组合若干列 + 若干规则」的列式校验，而不是被钉死在 7 字段表上。

为此先把后端规则系统从「按字段 key 分发」泛化为「按规则 id 分发」，并把校验规则从写死在行级逻辑里抽出来成为可枚举的规则记录。

### 改动

- `ExtractParams` 从单一形态扩展为 4 个变体（mask / extract / validate / 自定义），统一通过规则记录描述
- 新增 6 条 `kind=validate` 规则（函数式 + 正则），加上既有的 `name-validate`，共 7 条 validate 规则可供前端自由选择：
  - `username-validate`、`sex-validate`、`birth-validate`、`idcard-validate`、`phone-validate`、`address-validate`、`name-validate`
- 规则分发逻辑泛化：按 `ruleId` 查表 → 路由到对应校验函数
- DB seed 写入上述 7 条 validate 规则
- `idcard-validate` 规则支持 crossField（性别 / 出生日期比对）

### 不变项

- 既有 `validate_column` / `validate_rows_to_two_sheets` 命令保留（向后兼容）
- DB schema 不变（规则表已存在）
- capabilities/default.json 不变

### 验收项

- **E79**：`ExtractParams` 新增 4 变体（Username/Sex/Birth/Address），serde camelCase roundtrip 正确
- **E80**：`validate_extracted` 新增 4 分发分支，分别调 `is_valid_username` / `is_valid_sex` / `is_valid_birth` / `is_valid_address`，返回 `(bool, String)`
- **E81**：`with_defaults()` 注册 6 条新 validate 规则，内置规则总数 10 → 16；DB seed 幂等（老用户升级 upsert 插入新 id，现有 10 条不动）

## T68：新增 validate_multi_rules_to_two_sheets IPC 命令

### 背景

T67 把规则泛化为可枚举记录后，需要一个面向「多规则列式校验」的新命令承接前端统一校验页面：接收任意多条「列 + 规则」组合，一次校验后把通过 / 失败的行分流到两个新 Tab。

### 改动

- 新增 IPC 命令 `validate_multi_rules_to_two_sheets`
- 参数（全 camelCase）：
  - `sheetId: number`
  - `sessionId: number`
  - `rules: Array<{ column: string, ruleId: string, crossField?: { checkSex: boolean, sexColumn: string|null, checkBirth: boolean, birthColumn: string|null } | null }>`
  - `phonePrefixes: string[]`（可选，默认 []）
- 返回：
  - `{ validSheet: ParseResult, invalidSheet: ParseResult, invalidReasons: Array<{ sourceRow: number, field: string, reason: string }> }`
  - `ParseResult = { newSheetId: number, headers: string[], rowCount: number, skipped: number }`
- 落地模式与 `validate_rows_to_two_sheets` 一致：通过 / 失败行分别写入两个新 Tab，保留原列，不新增列
- capabilities/default.json 无需改动（自定义命令无需权限）

### 不变项

- 不改 `validate_rows_to_two_sheets` / `validate_column`（保留向后兼容）
- 不改 DB schema

### 验收项

- **E82**：`validate_multi_rules_to_two_sheets` 命令接收多条 `{column, ruleId, crossField?}` 组合，逐行逐规则校验（phone-validate→`is_valid_phone` / params 非空→`validate_extracted` / pattern 非空→正则 `is_match` / 其他→默认通过），整行分流到 `{源sheet名}_校验通过` / `_校验失败` 两个新 Tab，保留原列不新增
- **E83**：身份证跨字段联合校验 — 仅 `idcard-validate` 规则带 `crossField` 配置且 idcard 本身有效时触发：性别 `normalize_gender` vs `idcard_gender`、出生日期 `is_valid_birth` 后 `idcard[6..14]` 切片比对；6 条集成测试（all_rules_pass / mixed_pass_fail / idcard_cross_field_sex_mismatch / idcard_cross_field_birth_mismatch / regex_rule_validation / partial_mapping）全过

## R3 续轮：哈希函数 + DB 文件解析（T73-T76）

### 背景

用户在 v1.1.4 R2 qa_passed 后追加 2 个需求（仍属 v1.1.4）：

1. **哈希函数加密**：当前 CryptoPanel 只有 Base64 编解码。扩展加入 MD5 / SHA1 / SHA256 等哈希函数，对指定列做哈希变换（不可逆，输出 hex 小写）。
2. **DB 文件解析**：当前 `detect_format` 支持 csv/xlsx/json/jsonl/txt/log/sql/pcap/pcapng，但不支持直接打开 `.db`/`.sqlite`/`.sqlite3` 二进制 SQLite 数据库文件。新增 `DbReader` 数据源，打开外部 .db 文件并读取全部用户表数据。

用户明确指示：「全部完成等待我对于v1.1.4版本的手工验证」— 即 R3 流水线走完（含 QA）后**不自动 finalize**（不 merge、不 tag），等待用户手工验证。

### 设计决策

#### 1. 哈希逻辑放在 src-tauri（不放 crates/core）

沿用 v1.1.2 `base64_column` 先例：`base64` crate 依赖加在 `src-tauri/Cargo.toml`，`base64_transform_column_cells` DB 闭包式列变换方法写在 `src-tauri/src/db/mod.rs`，core 不引入 hash 依赖，保持 core 轻量。R3 同样把 `md-5`/`sha1`/`sha2`/`hex` 4 个 crate 依赖加在 `src-tauri/Cargo.toml`，`hash_column_inner` 在闭包内按 `HashAlgorithm` 分发调用对应 digest，复用既有 `base64_transform_column_cells<F: Fn(&str) -> Option<String>>`（闭包式签名与函数名无关，无需重命名，沿用既有调用链）。

#### 2. DbReader 表名用 quote_identifier 转义

SQLite 表名不能用 `?N` 参数绑定（参数绑定只用于值，不能用于标识符）。`DbReader` 的表名来源限定为 `sqlite_master`（受信系统表，`type='table' AND name NOT LIKE 'sqlite_%'`），用 `quote_identifier`（双引号包裹 + 内部双引号翻倍）做防御性转义后拼入 `SELECT * FROM "{table}"`。表名来自受信来源 + 转义处理，不存在 SQL 注入面。

## R4 续轮：手机号前缀配置 UX 统一（T77-T78）

### 背景

用户在 v1.1.4 R3 qa_passed 后追加 2 个需求（仍属 v1.1.4）：

1. **T77 特殊符号自定义白名单**：原 `ExtractParams::Generic` 的 `allow_special: bool`（全开/全关）改为 `allow_special_chars: String`，用户可自由填写允许的特殊字符（如 `_-.@`）。
2. **T78 手机号前缀配置 UX 统一**：
   - **手机号校验**：前缀白名单从 ValidatePanel 底部全局 Form.Item（所有规则共享）改为每行内嵌（选中 phone-validate 时展开 Select mode="tags"）。多行都选 phone-validate 时合并所有行前缀（去重）。

### 设计决策

#### T77：特殊符号 `allow_special: bool` → `allow_special_chars: String`

用户明确要求「特殊符号应该是可以随意填写的」。原 bool 全开/全关语义过粗（要么允许全部特殊字符、要么一个都不允许）。改为字符串白名单：空串 = 不允许任何特殊字符；非空如 `_-.@` = 仅允许这些字符。逐字符判定逻辑：`(is_digit && allow_digits) || (is_letter && allow_letters) || allow_special_chars.contains(c)`。serde 加 `#[serde(default)]` 向后兼容（旧 JSON 无此字段时默认空串）。

#### T78：前缀白名单从全局改为每行内嵌

原 ValidatePanel 底部全局 `Form.Item name="phonePrefixes"` 对所有 phone-validate 行共享同一白名单。用户期望「在下拉选择手机号规则后填写」——即每行内嵌前缀输入。改动：删除全局 Form.Item，在 Form.List 每行新增 `shouldUpdate` 监听 ruleId，仅 phone-validate 时展开 `Form.Item name={[name, "phonePrefixes"]}` 的 Select mode="tags"。`handleValidate` 中从所有 phone-validate 行收集前缀，去重合并后传后端。

#### T78：提取增加 phone_prefixes 运行时覆盖

`extract_validate_to_new_sheet` 命令新增 `phone_prefixes: Vec<String>` 参数（`extract_validate_to_new_sheet_inner` 对应 `phone_prefixes: &[String]`）。在 phone-extract 规则的候选校验循环里，若 `phone_prefixes` 非空，构造临时 `ExtractParams::PhonePrefix { allowed_prefixes: phone_prefixes.to_vec() }` 传给 `validate_extracted_with_params` 覆盖 DB rule.params；若为空保持原逻辑（用 DB rule.params）。ExtractPanel 新增 `isPhoneExtract` 判定 + 前缀白名单 Select + `handleExtractValidate` 收集 phonePrefixes 传 IPC。tauri.js `extractValidateToNewSheet` 新增 `phonePrefixes = []` 参数。

## R4 续轮：规则列表按名称排序（T79）

### 背景

用户要求「所有规则按照首字母顺序自动排序」。原 `list_rules` DB 查询使用 `ORDER BY id ASC`（按 kebab-case id 字符串排序），前端各面板（RulesPanel / MaskPanel / ExtractPanel / ValidatePanel）继承 DB 返回顺序不做二次排序。用户希望改为按规则显示名称的 Unicode 码点升序排列（ASCII 开头排前，中文按码点序）。

### 设计决策

经 AskUserQuestion 确认排序方式为「Unicode 码点排序」（非拼音、非 id）。单一改动点：`list_rules` 的 SQL `ORDER BY` 子句从 `id ASC` 改为 `name ASC`。所有前端消费者不做改动，自动继承新顺序。SQLite 的 `ORDER BY name ASC` 对 TEXT 列按 Unicode 码点逐字节比较（UTF-8 编码序与码点序一致），ASCII 大写字母（I=0x49）排在中文（姓=0x59D3）之前。

### T79 改动

#### 后端

- `src-tauri/src/db/mod.rs`：`list_rules` 方法 SQL `ORDER BY id ASC` → `ORDER BY name ASC`；doc comment 同步「按 name 升序（Unicode 码点排序）」
