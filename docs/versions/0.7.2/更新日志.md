# v0.7.2 更新日志

> SqlParseTool textarea 支持 `body|sql` 前缀语法，打通盲注二分还原链路（body_size 贯通）。
>
> 用户诉求（verbatim）：用户报告 v0.7.1 URL-decode 修复后「为什么没有完整恢复数据库有的盲注数据」，并附 5 条 URL-encoded SQLi payload（目标 `database()` 位 1，`>` 阈值 79/103/109/112/115）。
>
> 用户确认的设计决策（AskUserQuestion）：输入语法 = **前缀 `body|sql`（推荐）** — 每行 `<body_size>|<sql>`，无前缀行保持 `responseBodySize: null`（向后兼容非盲注 payload）。

## 根因

v0.7.1 修复了 URL-decode（regex 匹配层），但盲注还原链路仍断在 **body_size 缺失**：

- `frontend/src/components/SqlParseTool.jsx:58` 对所有行构造 `{ sql, responseBodySize: null, sourceIp: null }`
- `crates/core/src/logsign/blind/probe.rs:61-64`：`None => return Vec::new()` → 0 探针
- → `BlindAggregator::collect_from_probes` 收到空集 → `aggregate()` 空 → `reconstruct_database()` 空 → 用户看到「解析失败/空结果」

盲注还原**必须**有 body_size 才能区分 true 簇（`ascii>thr` 为真，body==true_size）vs false 簇（body!=true_size）。`mode_per_position_true_size` 依赖混合位置（body_size 不全同）选举 true 簇；无 body_size 变化 → 无混合位置 → 退化到 `min(body_size)` → 无法区分真假簇 → 0 还原。

## 次要真相：gap 如实说明

用户提供的 5 条 payload 阈值 79/103/109（true 侧）/ 112/115（false 侧），设 true char='p'(ascii=112)：

- `aggregate_position`（`aggregate.rs:466-469`）要求 `max_true+1 == min_false`，即 `109+1=110 ≠ 112` → **gap**
- → `status="insufficient_probes"`、`ascii_val=Some(112)`、`decoded_char=None`

严格自洽校验是取证工具的保守设计（ascii 落在 [110,112] 区间，缺 110/111 探针不能精确定位）。**本 patch 不放宽该校验**，在测试 + 文档如实说明：补 110/111 两条探针即可自洽还原 'p'。

## 变更明细

### T26-1 前端 SqlParseTool.jsx `body|sql` 前缀解析 + UI 文案（P0）

#### ① `onParse` 改造（`SqlParseTool.jsx:47-69`）

`lines.map` 内对每行做前缀解析（纯本地正则 `^(\d+)\|(.*)$`，无新依赖）：

```javascript
const inputs = lines.map((line) => {
  const m = /^(\d+)\|(.*)$/.exec(line);
  if (m) {
    const bodySize = Number(m[1]);
    const sql = m[2];
    return {
      sql,
      responseBodySize: Number.isFinite(bodySize) ? bodySize : null,
      sourceIp: null,
    };
  }
  return { sql: line, responseBodySize: null, sourceIp: null };
});
```

- 文件顶部注释（21-30 行）更新：说明 v0.7.2 起 textarea 支持 `body|sql` 前缀
- `onParse` 上方注释（57 行）从「response_body_size / source_ip 留空 None」改为说明前缀语法 + body_size 是盲注还原关键

### T26-2 core 单测 body_size 贯通还原 + 用户 5 payload gap 断言（P0）

新增 2 个测试，append 到 `crates/core/src/tools/sql_parse.rs` 现有 `mod tests`（紧邻 `parse_sqls_url_encoded_time_payload` 之后）：

#### ① `parse_sqls_body_size_enables_full_reconstruction`

用既有 helper `ascii_binary_probes_for_char("database()", 1, b'p' as u32, 862, 875, "1.1.1.1")` 生成 3 true + 2 false 自洽序列（helper 生成 `target-1=111` 作为 max_true，`target=112` 作为 min_false，`111+1=112` ✓ 自洽）。

断言：
- `result.probes.len() == 5`
- `result.aggregated.len() == 1`，`decoded_string.starts_with('p')`，`resolved_chars == 1`
- `result.reconstructed.schema.as_deref() == Some("p")`（单字符 database 名）
- `result.reconstructed.tables.is_empty()`

**回归对照**：同一组 input 但 `response_body_size: None`（模拟 v0.7.2 前行为）→ `result.probes.is_empty()` + `result.aggregated.is_empty()` + `result.reconstructed.schema.is_none()`，证明 body_size 是贯通的关键。

#### ② `parse_sqls_user_five_payloads_with_body_size_gap_documented`

构造用户提供的 5 条 URL-encoded payload，true 侧（79/103/109）body=862、false 侧（112/115）body=875：

```rust
let raw_payloads: &[(&str, u64)] = &[
    ("username=1'%20or%20ascii(substr((database()),1,1))%3E79%23&password=1", 862),
    ("username=1'%20or%20ascii(substr((database()),1,1))%3E103%23&password=1", 862),
    ("username=1'%20or%20ascii(substr((database()),1,1))%3E109%23&password=1", 862),
    ("username=1'%20or%20ascii(substr((database()),1,1))%3E112%23&password=1", 875),
    ("username=1'%20or%20ascii(substr((database()),1,1))%3E115%23&password=1", 875),
];
```

断言：
- `result.probes.len() == 5`（v0.7.1 URL-decode + v0.7.2 body_size 贯通后探针全部提取）
- `result.aggregated.len() == 1`
- position 1 `ascii_val == Some(112)`、`decoded_char == None`、`status == "insufficient_probes"`
- `decoded_string == "?"`（insufficient 插 '?'）
- `schema == Some("?")`

注释如实说明：gap=110/111，补齐后即自洽还原 'p'（ascii=112）。
