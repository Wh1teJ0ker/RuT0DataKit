# 04 — 版本标准

> 本文件定义 RuT0DataKit 的版本号语义、里程碑索引、版本状态口径与发布门禁。版本状态只能由 [`docs/qa/versions/<ver>/QA-审计报告.md`](./qa/versions/1.1.2/QA-审计报告.md) 结论驱动，不随主观声明改变。

## 1. 版本号语义

- 采用稳定版语义化版本 `MAJOR.MINOR.PATCH`，Git tag 格式 `vMAJOR.MINOR.PATCH`。
- 禁止 `-rc` / `-beta` / `-alpha` 等预发布后缀；只接受数字三段式正式版本。
- **v1.x 系列语义**：v1.x 为「框架与能力渐进重构」阶段。
  - `MAJOR=1`：表示 v1.0.0 起「从零重写」的新架构基线，与已归档的 v0.8.0 不兼容。
  - `MINOR`：能力里程碑。每个 minor 版本对应一组能力模块的完整重构与落地（见 §2 里程碑索引）。
  - `PATCH`：同一 minor 内的缺陷修复与小幅调整，不引入新能力模块。
- **唯一版本源**：`src-tauri/tauri.conf.json` 的 `version` 字段。`Cargo.toml`（根 + core + src-tauri）与 `frontend/package.json` 必须同步该值，不得手工维护多个可能漂移的版本常量。
- 应用版本、Git tag（去 `v` 前缀）、发布产物命名、版本文档目录必须一致。

## 3. 版本状态口径

| 状态 | 含义 | 是否可发布 |
|---|---|---|
| `planned` | 已规划范围，未开始实现 | 否 |
| `in_progress` | 已拆任务并分派实现，有任务进入 `verified_complete` | 否 |
| `done_e2e` | 本版本所有任务 `verified_complete` + 端到端集成验收通过 | 否 |
| `qa_passed` | Release QA 审计通过，`docs/qa/versions/<ver>/QA-审计报告.md` 结论为 `qa_passed` | 允许进入 finalize |
| `qa_failed` | QA 发现 major/critical 问题，需回流修复 | 否 |
| `blocked` | 缺少证据、凭据或环境能力（如签名密钥未就绪） | 否 |
| `release_complete` | finalize 成功 + 版本文档同步完成 + 公开 Release 已发布 | 已发布 |

约束：
- `qa_failed` 与 `blocked` 禁止任何形式的 finalize 或公开发布声明。
- `done_e2e` 不等于可发布；必须经 Release QA 审计推进到 `qa_passed` 才允许 finalize。
- `release_complete` 必须有真实 GitHub Release 产物证据，文档不得先于实际发布声明「已发布」。

## 4. 发布门禁

发布一个版本必须依次满足：

1. 本版本所有任务 `verified_complete`（见 [`03-开发任务清单.md`](./03-开发任务清单.md)）；
2. 端到端集成验收通过，状态 `done_e2e`；
3. Release QA 审计通过，`docs/qa/versions/<ver>/QA-审计报告.md` 结论为 `qa_passed`；
4. 版本文档同步完成：
   - `docs/versions/<ver>/规划需求.md`（范围与任务）
   - `docs/versions/<ver>/更新日志.md`（进度表与最终摘要，与 `handoff/TASK-BOARD.md` 一致）
   - `docs/qa/versions/<ver>/QA-审计报告.md`（审计结论）
5. Git tag `v<VERSION>` 打在已验证的提交上；
6. 签名 / 公证凭据就绪（Tauri updater 签名密钥 + GitHub Secrets），否则状态 `blocked`；
7. README 双语同步当前版本与发布产物信息。

CI 全绿、构建成功、产物存在都不足以单独放行发布。

## 5. Draft 与 Finalize 流程

遵循 Release 通用规范：

1. 校验 Git tag（去 `v`）与 `tauri.conf.json` version 一致；
2. 校验 Release QA 状态为 `qa_passed`；
3. 创建 draft Release（避免 `latest` 指针提前迁移）；
4. 四目标矩阵构建并上传产物（Linux x64 / macOS arm64 / macOS x64 / Windows x64）；
5. 生成并上传 SHA-256 checksums；
6. updater JSON（`latest.json`）随 Release 上传，仅在 finalize 后生效；
7. 所有质量门禁与全平台构建成功后，由独立 finalize job 将 draft 改为正式发布。

`finalize` 必须显式依赖全部上游 job 成功，失败任一即不执行。正式发布只面向稳定版 `vMAJOR.MINOR.PATCH` tag。

## 6. 产物命名

```
RuT0DataKit_<VERSION>_<PLATFORM>_<ARCH>.<EXT>
```

| 平台 | 架构 | 归档 |
|---|---|---|
| linux | x86_64 | `.tar.gz` |
| macos | aarch64 | `.zip` 或 `.dmg` |
| macos | x86_64 | `.zip` 或 `.dmg` |
| windows | x86_64 | `.zip` 或 `.msi` |

每个 Release 附 `checksums.txt`（每行 `<sha256>  <filename>`）。

## 7. 文档同步要求

以下变化发生后，对应文档必须同步：

- 里程碑索引变化 → 本文件 §2；
- 版本状态变化 → 本文件 §2 + `docs/versions/<ver>/更新日志.md` + `docs/qa/versions/<ver>/QA-审计报告.md`；
- Quick Start / 启动方式变化 → `README.md` + `README_EN.md`；
- 任务清单变化 → `03-开发任务清单.md` + `docs/versions/<ver>/规划需求.md` + `handoff/TASK-BOARD.md`。

`docs/versions/<ver>/更新日志.md` 的进度表必须与 `handoff/TASK-BOARD.md` 任务状态保持一致，冲突以实际验证证据为准。
